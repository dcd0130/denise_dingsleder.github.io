Overview

A relational database and console application covering Division I collegiate alpine ski race scheduling, built with a project partner — drawing on my own background as a Division I ski racer for the domain.

What We Built

The schema models race venues, per-venue contacts, and races themselves (sex, date, discipline, status), with a relocation-history table for races that move venues. The Java console application connects over JDBC and supports searching races, cancelling or relocating a race, managing contacts, adding new venues, and reporting (e.g. the highest-elevation venue via a subquery). Every query uses parameterized prepared statements rather than string-built SQL, which avoids SQL-injection risk by construction.

What We Learned

  • Skills: relational schema design (normalization, foreign keys), JDBC, parameterized queries, and translating a real domain (ski race scheduling) into tables.
  • Where it's used: parameterized/prepared statements are the industry-standard defense against SQL injection — literally how production applications protect their databases.
  • Reflection: designing the schema ourselves, rather than being handed one, was the real lesson — deciding what deserves its own table (like the relocation-history table) versus a status flag is a judgment call that shapes everything downstream.
Technical Deep-Dive: Schema & Prepared Statements

Fact tables vs. dimension tables. This schema splits cleanly into two kinds of tables, a pattern that shows up in almost every real database, not just data-warehouse designs. Location and Contact are dimension tables: relatively static, descriptive, lookup-style data — a resort's name only needs to be stored once, ever. Race is a fact table: every row is a discrete event (one race, on one date, at one location, with one contact), and it references the dimension tables by ID instead of repeating their details. The payoff is that if a resort's name changes, it's a one-row update in Location instead of a find-and-replace across every race ever held there — that's what "normalizing" a schema actually buys you.

The schema uses foreign keys with cascading/set-null rules so races stay consistent when a location or contact is removed:

CREATE TABLE `Race` (
  `id` int(11) NOT NULL AUTO_INCREMENT,
  `location_id` int(11) DEFAULT NULL,
  `contact_id` int(11) DEFAULT NULL,
  `sex` enum('F','M') NOT NULL,
  `date` date NOT NULL,
  `discipline` enum('GS','SL') NOT NULL,
  `status` enum('A','C','R') NOT NULL,
  PRIMARY KEY (`id`),
  CONSTRAINT `Race_ibfk_1` FOREIGN KEY (`location_id`) REFERENCES `Location` (`locationId`) ON DELETE SET NULL,
  CONSTRAINT `Race_ibfk_2` FOREIGN KEY (`contact_id`) REFERENCES `Contact` (`contactId`) ON DELETE SET NULL
);

Every query in the Java console app is a parameterized PreparedStatement, prepared once at connection time and reused — string values are always bound, never concatenated into the SQL, which rules out SQL injection by construction:

What that JOIN is mechanically doing. Race only stores location_id, a bare number — on its own it can't tell you the resort's name. INNER JOIN Location ON Location.locationId = Race.location_id tells the database: for every row in Race, go find the one row in Location whose ID matches, and glue the two rows together into one wider row for the duration of this query. Nothing is duplicated in storage — the join happens on the fly, at query time — which is exactly why splitting the data into a fact table and dimension tables in the first place doesn't cost you the ability to ask a question like "every race at Snowbird" in a single query.
