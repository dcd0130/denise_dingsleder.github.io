Textual Analysis: WSJ & S&P 500

Textual Analysis in Business · 4-person team · Python / NLP · May 2024

  • Python
  • spaCy NER
  • REST API Integration
  • pandas

Overview

An exploratory project asking an event-study-style question: does a company's stock price move around obituary news coverage of people tied to that company — executives, founders, board members? The project combines a live news API with NLP entity extraction and financial market data to build a pipeline for testing that question.

What We Built

As a 4-person team, we integrated the Wall Street Journal's article API (via RapidAPI) to search and retrieve obituary coverage, used spaCy's named-entity recognition to extract people and organizations from article text, cross-referenced the companies mentioned against a S&P 500 company list, and wrote a pipeline to look up each company's ticker and pull historical closing prices around the article's publication date. My focus was the NER extraction and the ticker/price lookup pipeline.

What We Learned

  • Skills: consuming a live REST API, NLP entity extraction with spaCy, joining unstructured text data to structured financial data, and handling real-world data-matching failures gracefully instead of hiding them.
  • Where it's used: event-study methodology (does news move a stock) is a genuine quant-research technique, and API + NLP pipelines like this one are core to alternative-data research at funds.
  • Reflection: the real lesson here came from what broke, not what worked — the company-tagging problem in the underlying data (see "What We Found" below) mattered more to the result than the NLP or event-study code itself. It taught me to treat a pipeline's output as suspect until I've checked the data feeding it, not just the code processing it.

What We Found

The pipeline ran end-to-end — search, NER, ticker lookup — but it surfaced a data-quality problem before it ever reached stock prices: the WSJ API's own company-tagging turned out to be unreliable. Across the 17 (company, article) pairs the API returned, only 6 distinct obituaries were actually represented, and most of the company tags had no real connection to the person who died. Anne Innis Dagg, a giraffe researcher, was tagged to American Tower, Booking Holdings, and Invitation Homes; O.J. Simpson's obituary was tagged to American Tower, Brown & Brown, Otis Worldwide, and Robert Half — none of these companies have any evident link to either person. Only one obituary (Donald E. Petersen, a former Ford CEO) was correctly tagged to its real company, Ford Motor Company — but it was also wrongly tagged to five others.

That's the honest headline result: the entity-linking step, not the price lookup, turned out to be the real bottleneck. A trustworthy version of this study would need its own company-matching — for example, running the spaCy NER output against a real list of each company's executives and board members — rather than relying on the API's tagging. Surfacing that is exactly what a proof-of-concept pipeline is supposed to do.

Technical Deep-Dive: NLP & API Pipeline

What "named-entity recognition" is actually doing. It would be simple, but brittle, to just scan obituary text for a hard-coded list of company names. spaCy's en_core_web_sm model does something different: it's a statistical model trained on large amounts of labeled text to recognize the pattern of how organization names, person names, dates, and places tend to appear in a sentence — capitalization, surrounding words, position — and predicts a label (ORG, PERSON, DATE, ...) for each span of text, with a confidence behind that prediction. That's what makes it generalize to company names never seen during training, and it's also exactly why it can mislabel or miss things in messy real-world text — it's a prediction, not a lookup.

My part of the shared pipeline: named-entity recognition on obituary text with spaCy, then a ticker/price lookup against the WSJ API. Entity extraction:

nlp = spacy.load("en_core_web_sm")

doc = nlp(content)
for ent in doc.ents:
    print(ent.text, ent.start_char, ent.end_char, ent.label_)

Each extracted company name is matched against the S&P 500 list, then looked up for a ticker and closing price around the article's publish date via the WSJ RapidAPI endpoint:

def get_ticker_symbol(company_name):
    url = "https://wall-street-journal.p.rapidapi.com/api/v1/searchCompanyByKeyword"
    headers = {
        "X-RapidAPI-Key": "YOUR_RAPIDAPI_KEY",
        "X-RapidAPI-Host": "wall-street-journal.p.rapidapi.com"
    }
    querystring = {"keyword": company_name}
    response = requests.get(url, headers=headers, params=querystring)
    if response.status_code == 200:
        data = response.json()
        if data['data'] and len(data['data']) > 0:
            return data['data'][0]['ticker']
    return None

The data-quality problem described above (in "What We Found") is visible directly in the raw CSV the API returned — grouping by headline shows the same obituary tagged to several unrelated companies:

>>> df.groupby('headline')['company name'].apply(list)

"O.J. Simpson, Whose Murder Trial..."   [American Tower, Brown & Brown, Otis Worldwide, Robert Half]
"Anne Innis Dagg, Giraffe Researcher..." [American Tower, Booking Holdings, Invitation Homes]
"Donald E. Petersen, Who Boosted..."    [Ball Corporation, Boeing, Ford Motor Company, General Motors, ...]

None of O.J. Simpson's four tagged companies, and only one of Donald Petersen's six, have any real connection to the person — which is what made the ticker/price-lookup step downstream fundamentally unreliable, independent of the API rate limits or ticker-matching gaps.
